# Three-node controller advancement walkthrough

Updated November 4, 2026 for controller 0.6.1 and nodes 0.6.0. The host sends
only a destination for each simulated new head. The controller computes and
applies ACTIVE/LAST/HOLD_OPEN/OFF. The binary application interface and event
identity/replies remain deferred; this is a deliberate bench invocation per head.

| Step | Input/event | Node1 | Node2 | Node3 |
| --- | --- | --- | --- | --- |
| 0 | Initialize new auction | OFF | OFF | OFF |
| 1 | Destination 1 | ACTIVE | OFF | OFF |
| 2 | Destination 1 again | HOLD_OPEN | OFF | OFF |
| 3 | Destination 2 | LAST | ACTIVE | OFF |
| 4 | Destination 2 again | LAST | HOLD_OPEN | OFF |
| 5 | Destination 3 | OFF | LAST | ACTIVE |
| 6 | Destination 3 again | OFF | LAST | HOLD_OPEN |
| 7 | Destination 2 again | OFF | ACTIVE | LAST |
| 8 | Destination 1 | ACTIVE | LAST | OFF |
| 9 | Finish/new-auction clear | OFF | OFF | OFF |

ACTIVE = solid green; LAST = solid blue; HOLD_OPEN = flashing green. Each row
holds until the user requests `next`. `start` initializes OFF and `stop` performs
explicit new-auction clearing. No timer advances the test. No light state is
sent by the host on a destination row. Live polls verify all three expected
states after each operation; the user supplies physical color/flashing confirmation.

On Lin, use the UART virtual-environment Python with `scripts/flow_walkthrough.py`
and action `plan`, `start`, `next`, `status` or `stop`. Local test progress is
saved under ignored build/. If delivery/polling fails, the host stops advancing.
Query `FLOW` to resolve an ambiguous result; do not repeat DEST as a retry.
Controller `FLOW=RETRY` resumes paused work, or use explicit new-auction clear.
FULL/FAULT remain outside normal advancement and are not generated by this test.
The prior manual-state walkthrough was prepared but never started; this version
is intended to validate actual controller-owned advancement after upload.
